# Personal Finance Track Manager

A **Blazor Server** personal finance tracking app using **Dapper** and **SQL Server stored procedures**.
Cookie-based authentication with Admin/User roles - Admin manages the system and observes
aggregate data across every user; User owns their own accounts, categories, and transactions.
An Admin account never has financial data of its own.

## Project Structure

```
PersonalFinanceTracker/
├── Components/
│   ├── Account/          # Login, Register (static SSR - see the Auth section below)
│   ├── Layout/           # MainLayout, AuthLayout, NavMenu
│   ├── Pages/            # Dashboard, Transactions, Accounts, Categories, Reports, Users
│   └── Shared/           # SummaryCard, MonthlyChart, TransactionForm
├── Services/             # Business logic (interfaces + implementations)
├── Repositories/         # Dapper data access (interfaces + implementations)
├── Models/               # Domain models and form DTOs
├── Data/                 # DbConnectionFactory
├── Database/
│   ├── Schema.sql        # Table creation (Users, Accounts, Categories, Transactions)
│   ├── SeedData.sql      # Seeded Admin + Demo User, sample data owned by Demo User
│   └── StoredProcedures.sql  # CRUD + calculations, all scoped by @UserId
├── Program.cs            # DI wiring, cookie auth, /Account/Logout endpoint
└── appsettings.json      # Connection string
```

## Authentication & Roles

- **Admin** ([Authorize(Roles = "Admin")]) - sees system-wide dashboard/reports/transactions
  across every user, and manages users on the `/users` page (promote/demote role, activate/
  deactivate). Can't manage Accounts/Categories - an Admin has none of its own.
- **User** ([Authorize(Roles = "User")] on Accounts/Categories, plain [Authorize] elsewhere) -
  owns their own accounts, categories, and transactions; every query is scoped to their UserId,
  both in the C# layer and by a stored-procedure-level ownership check.
- Self-registration (`/Account/Register`) only ever creates a `User` account. The one seeded
  Admin lives in `SeedData.sql`, with a password hash generated by actually running
  `PasswordHasher<T>.HashPassword` (not hand-typed), so it logs in correctly on a fresh database.
- Two seeded logins after running the database scripts:
  - Admin: `admin@financetrack.local` / `Admin@123`
  - Demo User (owns all the sample data below): `demo@financetrack.local` / `Admin@123`
- Guards against locking everyone out: `UserService.SetRoleAsync`/`SetActiveAsync` refuse to
  demote or deactivate the only remaining (active) admin.

## Prerequisites

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- **SQL Server** or **LocalDB** (included with Visual Studio)

## Database Setup

Run the SQL scripts **in order** using SQL Server Management Studio, Azure Data Studio, or `sqlcmd`:

1. `Database/Schema.sql`
2. `Database/SeedData.sql`
3. `Database/StoredProcedures.sql`

**Using sqlcmd (LocalDB):**

```powershell
sqlcmd -S "(localdb)\mssqllocaldb" -i Database\Schema.sql
sqlcmd -S "(localdb)\mssqllocaldb" -d PersonalFinanceTracker -i Database\SeedData.sql
sqlcmd -S "(localdb)\mssqllocaldb" -d PersonalFinanceTracker -i Database\StoredProcedures.sql
```

Update the connection string in `appsettings.json` if you use a different SQL Server instance.

## Run the App

```powershell
cd PersonalFinanceTracker
dotnet restore
dotnet run
```

Open the URL shown in the terminal (typically `https://localhost:5xxx`).

You can also open the `.csproj` in **Visual Studio** or **Rider** and press F5.

## Features

- **Dashboard** — User: balance, monthly income/expenses, savings rate, category breakdown.
  Admin: the same shape, aggregated across every user (active user count, total balance,
  monthly income/expenses, transaction count).
- **Transactions** — User: add, edit, delete income/expense entries. Admin: every user's
  transactions, read-only, with a "User" column.
- **Accounts** — User-only: manage checking, savings, credit, investment accounts.
- **Categories** — User-only: organize income and expense types.
- **Reports** — User: 6-month trends, savings rate, category analysis. Admin: the same
  reports aggregated across every user.
- **Users** — Admin-only: promote/demote roles, activate/deactivate accounts, with guards
  against demoting or deactivating the last remaining admin.

## Stored Procedures

| Procedure | Purpose |
|-----------|---------|
| `usp_User_*` | Auth/user management (create, lookup by email, list, set role/active, admin counts) |
| `usp_Account_*` | Account CRUD, scoped to `@UserId` |
| `usp_Category_*` | Category CRUD, scoped to `@UserId` |
| `usp_Transaction_*` | Transaction CRUD (auto-updates account balance), scoped to `@UserId` with ownership checks on the Account/Category involved |
| `usp_Transaction_GetAllForAdmin` | Every transaction across every user, joined to Users |
| `usp_Dashboard_GetSummary` / `usp_Dashboard_GetSystemSummary` | Per-user / Admin all-users dashboard totals |
| `usp_Report_GetMonthlyTotals` / `...AllUsers` | Per-user / Admin all-users monthly income/expense/net |
| `usp_Report_GetCategoryBreakdown` / `...AllUsers` | Per-user / Admin all-users category spending breakdown |
| `usp_Report_CalculateSavingsRate` | Per-user savings rate calculation |
